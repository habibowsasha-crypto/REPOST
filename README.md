# ❤️ LikeBot v1.0.44b

Управляющий Telegram-бот для собственных и добровольно подключённых аккаунтов: авторизация через MTProto, подписка на каналы и группы, реакции на новые и старые публикации, интервалы выполнения и сохраняемые очереди.

> Проект не содержит обхода Telegram FloodWait, подмены устройств, прокси-ротации или механизмов обхода блокировок. Ограничения Telegram всегда имеют приоритет.



## Hotfix живых разговоров по контексту пяти постов - шаг 12, v1.0.44b

Версия построена строго от v1.0.44a после живого теста, где ответы всё ещё
выглядели как точный опрос и справочная служба. Публикация в Telegram по-прежнему
отсутствует.

Изменено:

- prompt обновлён до `dialogue-reply-v3`, validator до
  `dialogue-reply-validator-v3`;
- диалог получает текущий пост и ещё до четырёх ближайших предыдущих публикаций
  как единый фон последних пяти постов;
- введены разные режимы хода: реакция, короткое мнение, лёгкая шутка, подколка,
  неполный ответ, соседняя тема, мягкое завершение;
- вопрос, точный ответ и полезный факт больше не обязательны для каждой реплики;
- разрешены small talk, лёгкая ирония, смайлы и естественный уход на соседнюю
  тему из последних пяти постов;
- запрещён стиль поддержки: шаблонные запросы про точные условия, статистику и
  подтверждения, а также ответы «значит, стоит искать» и «следует уточнить»;
- factual claims не требуются для шутки, реакции или субъективного мнения;
- БД, лимиты и переменные Railway не менялись.

Для проверки создаётся полностью новый диалог. Старые черновики сохраняют
исторические версии prompt.


## Hotfix естественности связанных диалогов - шаг 12, v1.0.44a

Версия v1.0.44a построена строго от подтверждённого кандидата v1.0.44 после
живого Railway-теста, который показал технически правильные, но слишком
формальные и повторяющиеся реплики. Публикация в Telegram по-прежнему
физически отсутствует.

Исправлено:

- prompt диалогов обновлён до `dialogue-reply-v2`;
- в каждый запрос теперь явно передаются тон, словарь, шаблон предложений,
  пунктуация, любимые слова, уровень знаний и роль конкретного профиля;
- модель получает отдельную цель текущей позиции: реакция на пост, ответ,
  новый нюанс, мягкое возражение или действительно новый вопрос;
- запрещены канцелярские обороты и формальные отчётные вступления;
- следующая реплика обязана добавлять новый смысл, а не пересказывать вопрос,
  числа или вывод предыдущего участника;
- validator `dialogue-reply-validator-v2` отклоняет дословные повторы,
  семантические пересказы, повтор уже заданного вопроса и типичные
  бюрократические формулировки;
- финальная реплика должна закрывать разговор естественно, без формального
  резюме;
- schema и БД не менялись, миграция не требуется.

Для проверки после deploy нужно создать новый диалог. Старые черновики,
сгенерированные prompt v1, не переписываются автоматически.

## Связанные AI-диалоги и суточные лимиты - шаг 12, v1.0.44

Версия v1.0.44 построена строго от принятого кандидата v1.0.43 и добавляет
конечные связанные диалоги только в виде черновиков. Публикация в Telegram
по-прежнему физически отсутствует.

Добавлено:

- конечный thread-план на 2-5 выбранных профилей и 2-5 реплик;
- каждая следующая реплика имеет точный `reply_to` на предыдущую одобренную
  реплику и получает всю уже одобренную ветку;
- один AI-вызов создаёт только одну следующую реплику; администратор отдельно
  принимает или отклоняет её;
- состояние `planned → generating → review → planned/completed`, отмена,
  `max_messages`, `expires_at`, проверка ревизии корневого поста и dedup;
- индивидуальный базовый лимит комментариев аккаунта за календарные сутки;
- настраиваемый бонусный пул ответов `0-20`, по умолчанию `3`: он открывается
  один раз за сутки, когда зафиксирован реальный внешний ответ на уже
  опубликованный комментарий этого профиля;
- бонусные слоты разрешены только для ответа в существующей ветке и только
  после исчерпания базового дневного лимита; обычные комментарии их не тратят;
- счётчики переключаются на новый календарный день ровно в `00:00` по
  `AI_COMMENTS_TIMEZONE` (по умолчанию `Europe/Moscow`) без фонового reset-job;
- выдача и расход бонусов идемпотентны, а PostgreSQL-потребление защищено
  блокировкой строки профиля;
- schema v4 добавляет `ai_comment_thread_plans` и `ai_comment_quota_events`;
  итоговая схема содержит 28 таблиц: 11 core и 17 изолированных `ai_`-таблиц.

Новые переменные с безопасными значениями по умолчанию:

```text
AI_DIALOGUE_MAX_MESSAGES=5
AI_DIALOGUE_MIN_INTERVAL_SECONDS=60
AI_DIALOGUE_MAX_INTERVAL_SECONDS=600
AI_DIALOGUE_EXPIRES_HOURS=24
AI_COMMENTS_TIMEZONE=Europe/Moscow
```

Для первого Railway deploy все AI-флаги остаются `false`. После чистого startup
для ручного теста включаются только gateway, comments, generation и dialogues;
`AI_PUBLICATION_ENABLED` остаётся `false`.

> Шаг 12 не наблюдает Telegram-ответы в production и не расходует bonus slots
> при отправке, потому что publication/observer worker относится к шагу 15.
> Сейчас готовы схема, бизнес-правила, UI и тестируемые hooks для этой интеграции.

## Один AI-комментарий только в черновик - шаг 11, v1.0.43

Версия v1.0.43 построена строго от принятого кандидата v1.0.42 и реализует
ручную генерацию ровно одного комментария без Telegram-публикации.

Добавлено:

- отдельный context builder для выбранного канала, конкретной ревизии поста,
  профиля аккаунта, последних публикаций и только проверенных knowledge chunks;
- versioned prompt `single-comment-v1` и строгая Structured Output schema
  `single-comment-schema-v1` с двумя решениями: `draft` или `skip`;
- локальный валидатор проверяет длину, confidence, ссылки, гарантии, запрещённые
  темы/утверждения, неподтверждённые числа, provenance текущего поста, evidence
  quotes и длинное дословное копирование;
- профиль канала и профиль стиля нельзя использовать как доказательство
  рыночного факта; factual claim принимается только со ссылкой на пост,
  сценарий, предыдущий пост или проверенный knowledge chunk;
- источник перепроверяется по `source_revision` и SHA-256 перед запросом и перед
  сохранением; изменившийся пост отбрасывает результат;
- результат сохраняется в существующих `ai_generation_jobs`,
  `ai_comment_drafts` и `ai_usage_stats` как `pending_review`, `skip` или
  `rejected`; publication job не создаётся;
- UI: пост → `✍️ Создать один черновик` → профиль → отдельное подтверждение →
  результат с provenance, prompt/schema versions и причинами отклонения;
- раздел `✅ Черновики` показывает последние draft/skip/rejected записи;
- генерация разрешена только при одновременном включении общего флага,
  generation-флага и OpenAI Gateway в Railway и БД;
- диалоги и публикация остаются заблокированными и выключенными.

Новые необязательные переменные имеют безопасные defaults:

```text
AI_GENERATION_MAX_OUTPUT_TOKENS=512
AI_GENERATION_RECENT_POSTS=5
AI_GENERATION_KNOWLEDGE_CHUNKS=4
```

Миграция БД с v1.0.42 не требуется: используются существующие 26 таблиц.
Первый deploy выполняется со всеми AI-флагами `false`; после проверки startup
для одного теста включаются только `OPENAI_GATEWAY_ENABLED`,
`AI_COMMENTS_ENABLED` и `AI_GENERATION_ENABLED`. `AI_DIALOGUES_ENABLED` и
`AI_PUBLICATION_ENABLED` должны оставаться `false`.

## Безопасный OpenAI DEV Gateway - шаг 10, v1.0.42

## Индивидуальные профили аккаунтов LikeBot AI Comments - шаг 9

Версия v1.0.40 реализует только утверждённый шаг 9: постоянную индивидуальную
личность каждого подключённого аккаунта. OpenAI API, генерация комментариев и
Telegram-публикация не подключены.

- при добавлении аккаунта профиль создаётся автоматически и детерминированно по
  стабильному Telegram ID, но остаётся выключенным до решения администратора;
- пять офлайн-presets задают новичка, знающего основы, торопливого, осторожного
  и сомневающегося участника; API для их создания не используется;
- профили проверяются на избыточное сходство, имеют постоянный `persona_key` и
  не меняются после перезапуска или повторной авторизации;
- удаление core-аккаунта не удаляет личность: при возврате того же Telegram ID
  сохраняются имя, стиль, лимиты и вся история;
- UI поддерживает просмотр, постраничный список, редактирование, включение,
  выключение, обратимое архивирование, восстановление и новый характер;
- проверяются уровень знаний, роль, длина, emoji/question/reply/disagreement
  rates, любимые слова, разрешённые/запрещённые утверждения, дневной лимит и
  cooldown;
- каждое фактическое изменение создаёт неизменяемую revision с каноническим JSON
  и SHA-256; устаревшая форма не перезаписывает более новую версию;
- экран истории показывает revisions и уже существующие опубликованные реплики,
  не создавая новых сообщений;
- readiness guard блокирует профиль, если он выключен, архивирован, отвязан,
  аккаунт отключён/quarantined, статус не `ready`, нет готовой сессии, действует
  FloodWait, исчерпан дневной лимит или ещё идёт cooldown;
- ошибка автоматического создания профиля изолирована и не откатывает успешно
  сохранённую Telegram-авторизацию.

Schema AI Comments обновлена с v2 до v3: добавлена таблица
`ai_account_profile_revisions` и уникальная связь профиля со стабильным Telegram
ID. После upgrade в базе 26 таблиц - 11 core и 15 изолированных `ai_`-таблиц.
Существующие аккаунты получают выключенные профили автоматически, а старые
профили - первую revision `backfill`. Процедура описана в
`migrations/AI_COMMENTS_SCHEMA_V3.md`.

Миграция БД с v1.0.39 требуется. Перед deploy нужен backup, а все AI-флаги
должны оставаться `false`.

## Память каналов LikeBot AI Comments - шаг 8

Версия v1.0.39 реализует только утверждённый шаг 8: раздельную память каналов,
фактический профиль автора и аудит редакций публикаций. OpenAI API, генерация
комментариев, профили аккаунтов-комментаторов и Telegram-публикация ещё не
реализованы.

- память всегда выбирается по внутреннему ID конкретного канала и никогда не
  подставляет другой канал при устаревшем callback;
- существующий monitor при эффективном `AI_COMMENTS_ENABLED=true` сохраняет
  актуальные публикации через уже подключённые аккаунты; есть ручное обновление;
- операционное окно содержит последние 10 публикаций, а более старые записи не
  удаляются из аудита;
- повторная доставка одного Telegram message идемпотентна, устаревшая редакция
  отклоняется, удаление создаёт tombstone, восстановление не создаёт новый пост;
- каждая фактическая версия поста хранится в отдельной неизменяемой revision с
  причиной `ingested`, `edited`, `metadata`, `deleted`, `restored` или `backfill`;
- Telegram-альбом нормализуется как одна публикация с подписью и временем
  последнего изменения;
- администратор вручную редактирует тему, описание, аудиторию, стили, термины,
  методологию, разрешённые/запрещённые темы, рекламные ограничения и сводку;
- профиль имеет optimistic version guard и не допускает потерю параллельной
  правки;
- активные торговые сценарии создаются отдельно для каждого канала, связываются
  только с его постами и завершаются с сохранением истории;
- экраны «Память канала» и «Последние посты» показывают реальные данные БД,
  редакции поста и актуальные сценарии;
- ошибка AI-memory остаётся изолированной и не блокирует прежние задания реакций;
- новые модули не импортируют OpenAI и не создают generation/publication jobs.

Схема AI Comments обновлена с v1 до v2: добавлена таблица
`ai_channel_post_revisions`. После upgrade в базе 25 таблиц - 11 прежних и 14
изолированных `ai_`-таблиц. Существующие посты v1 автоматически получают
ревизию `backfill`; повторный upgrade идемпотентен. Процедура описана в
`migrations/AI_COMMENTS_SCHEMA_V2.md`.

Миграция БД с v1.0.38 требуется. Перед deploy нужен backup, а все AI-флаги
должны оставаться `false`.

## Схема LikeBot AI Comments - шаг 6

Версия v1.0.37 реализует только утверждённый шаг 6: изолированную схему БД и
идемпотентную миграцию. Генерация комментариев, OpenAI API, меню, AI workers и
Telegram-публикация ещё не реализованы и не запускаются.

- добавлены 13 таблиц с префиксом `ai_`; прежние 11 таблиц и их данные не
  преобразуются;
- migration поддерживает fresh/legacy/idempotence для SQLite и компилируется для
  PostgreSQL;
- generation и publication queues разделены, имеют idempotency keys, статусы,
  locks, retries и безопасные ошибки;
- draft хранит immutable revision, source post revision/hash и optimistic
  `lock_version`; ручная правка в будущих шагах не должна перезаписывать оригинал;
- knowledge source/chunk сохраняют source key, SHA-256, страницу, review status и
  eligibility; `needs_review` нельзя пометить индексируемым на уровне CHECK;
- удаление `channels`/`accounts` использует `SET NULL`, поэтому минимальный аудит
  approved/published решений не уничтожается;
- SQLite включает объявленные foreign keys на каждом соединении; полный прежний
  regression-набор продолжает проходить;
- отдельный CLI выполняет upgrade, verify и защищённый rollback; процедура backup
  и удаления только AI-таблиц описана в `migrations/AI_COMMENTS_SCHEMA_V1.md`;
- release verifier проверяет все 24 таблицы, ключевые индексы и PostgreSQL DDL.

Безопасные значения первого deploy:

```text
AI_COMMENTS_ENABLED=false
AI_COMMENTS_MODE=preview_only
AI_GENERATION_ENABLED=false
AI_DIALOGUES_ENABLED=false
AI_PUBLICATION_ENABLED=false
AI_DEBUG_SNAPSHOTS_ENABLED=false
```

Миграция БД требуется. На первом deploy все AI-флаги должны оставаться

## Глубокое runtime-усиление v1.0.33

Версия v1.0.33 закрывает найденные после завершения исходного плана гонки и дефекты fail-closed поведения:

- resolve, join/leave, get_messages, реакции и просмотры сериализованы стабильным task-owned lock каждого аккаунта;
- quarantine/drop не могут отключить client, пока другая task выполняет MTProto-запрос;
- worker после ожидания lock перечитывает account/target и не действует по удалённой или выключенной записи;
- auth failure сразу закрывает claimed job, а не оставляет его зависшим в `running`;
- join/leave queue защищена от stale worker: более новое противоположное действие нельзя затереть старым complete/retry/fail;
- private invite fallback срабатывает только на явный `TargetNotVisibleError`, не на network/FloodWait/auth ошибки;
- supervisor не скрывает падение или самопроизвольную cancellation worker одновременным завершением polling;
- critical alert state безопасно объединяется после временной ошибки БД;
- deterministic ZIP содержит один manifest и заранее валидирует диапазон `SOURCE_DATE_EPOCH`.

Схема базы, migrations, Railway Variables и callback_data не менялись.

## Автоматизация релизов v1.0.32

Этап 14 добавляет fail-closed release pipeline без изменения Telegram-логики и схемы базы:

- `python tools/release.py verify` проверяет исходное дерево, версию в документации, hash-lock зависимостей, Ruff, AST/compileall/tabnanny, дубли определений, опасные вызовы, секреты, PostgreSQL DDL, реальный временный SQLite и полный pytest;
- `--require-postgres --postgres-url ...` делает live PostgreSQL init/idempotence обязательным и завершает проверку ошибкой, если база недоступна;
- `python tools/release.py build --previous-archive ... --output-dir dist --tag ...` повторяет проверки, создаёт воспроизводимый ZIP, подписанный хешами manifest, git-compatible patch, аудит, JSON-отчёт и SHA-256;
- каждый ZIP имеет один корневой каталог и `RELEASE-MANIFEST.json`; path traversal, symlink, case-collision, секретные env, БД, сессии, логи, приватные ключи и вложенные архивы отклоняются;
- patch сначала проверяется через `git apply --check`, затем применяется к предыдущему архиву и побайтово сравнивается с новым staged tree;
- финальный ZIP распаковывается в чистый временный каталог и повторно проходит manifest, static, SQLite и pytest-проверки;
- `.github/workflows/release-validation.yml` запускает тот же verifier с отдельным PostgreSQL service на push, pull request и вручную.

Команды для обычной проверки:

```bash
python tools/release.py verify --report release-verify.json
```

Команда для production-кандидата с обязательным PostgreSQL:

```bash
python tools/release.py build \
  --previous-archive ../laika_bot_v1_0_31_architecture_modularization_ready.zip \
  --output-dir dist \
  --tag release_automation \
  --require-postgres \
  --postgres-url "$RELEASE_POSTGRES_URL"
```

Сборка без live PostgreSQL допустима только как offline-кандидат: DDL и SQLite всё равно проверяются, а JSON-отчёт честно фиксирует пропуск live-проверки. `--skip-tests` доступен только для диагностической команды `verify` и никогда не используется командой `build`.

- обновлённое компактное меню в две колонки и единый визуальный стиль карточек;
- отдельный экран настроек, карточки канала, аккаунтов канала и статистики канала;
- совместимая миграция базы v1.0.0-v1.0.29, включая `BIGINT`, раздельные очереди, индивидуальные реакции целей, лимит на пост, период раскрутки, очередь просмотров, историю проблемных аккаунтов и почтовые логины аккаунтов;
- максимум до 100 аккаунтов на один канал/группу;
- кнопка `➕ Подключить аккаунты: N` в карточке канала с подключением всех недостающих или ручным выбором;
- адаптивный лимит новых реакций для каждой публикации с безопасным случайным tie-break;
- отдельный таймфрейм раскрутки канала: 1-365 дней или команда `постоянный`.

## Критические уведомления администратору v1.0.25

Дополнительный supervised worker `critical-alert-monitor` раз в заданный интервал проверяет подтверждённые операционные состояния и отправляет сообщения только администратору:

- недоступность PostgreSQL/SQLite во время работы;
- отсутствие запуска, stale/blocked или длительное warning-состояние критического worker;
- очередь с большим backlog либо задания, зависшие в `running`;
- появление проблемных аккаунтов;
- FloodWait одновременно у большого количества аккаунтов;
- накопленные ошибки аккаунтов/целей;
- резкий рост terminal `failed` в очередях подписок, реакций и просмотров;
- аварийное завершение polling или любой supervised-задачи перед перезапуском Railway.

Состояние инцидентов хранится в существующей таблице `app_settings` под служебным ключом. Повтор одного и того же события ограничен cooldown, после нормализации приходит одно сообщение о восстановлении. Отправка одного уведомления ограничена `ALERT_SEND_TIMEOUT_SECONDS`, поэтому зависший Bot API не блокирует worker или перезапуск бесконечно. Несколько проблем одного цикла объединяются в ограниченные пакеты: критические события отправляются первыми, а не поместившиеся переходят в следующее сообщение и не считаются доставленными. Тексты исключений сокращаются, HTML экранируется, строки, похожие на Bot API token, пароль, API hash или URL с учётными данными, редактируются.

Уведомления являются только диагностикой: они не меняют очереди, не снимают FloodWait, не включают аккаунты и не пытаются автоматически обходить ограничения Telegram. Новых таблиц, колонок и обязательной ручной миграции в v1.0.25 нет.

## Адаптивное распределение нагрузки v1.0.24

Новые задания больше не получают аккаунты только по случайной выборке или порядку ID. Планировщик использует проверяемые данные LikeBot:

- число текущих `pending` и `running` во всех очередях;
- успешные и ошибочные задания за последние 24 часа;
- время последнего действия и длительность отдыха;
- активный FloodWait и его окончание;
- текущий статус и активность сохранённой сессии.

Аккаунт с меньшей нагрузкой и более долгим отдыхом получает приоритет. Активный FloodWait не обходится: такой аккаунт остаётся только резервом, а его задание переносится не раньше окончания ограничения. Старые totals не создают вечный штраф. При одинаковых показателях используется небольшой безопасный случайный tie-break.

Механика применяется к новым подпискам, недостающим подпискам существующего канала, реакциям, ручным просмотрам и выбору аккаунта для чтения канала. Административный выход сохранён отдельно, чтобы выключенные аккаунты не исключались из очистки членства.

Новых таблиц, колонок и Railway Variables в v1.0.24 нет.

## Hardening очередей и истории v1.0.23

Версия добавляет контроль возраста выполняющихся заданий и безопасную retention-политику:

- `running` старше 5 минут отдельно отображаются как зависшие;
- одна попытка реакции ограничена `REACTION_ATTEMPT_TIMEOUT_SECONDS`;
- timeout не теряет задание: оно возвращается в retry либо завершается failed после лимита попыток;
- старые terminal-строки реакций и просмотров архивируются не более чем по `JOB_HISTORY_CLEANUP_BATCH_SIZE` строк каждого типа за цикл;
- `join_jobs` не очищается, потому что это актуальное состояние членства account/channel, а не append-only журнал;
- агрегированные totals сохраняются по аккаунту и по каналу;
- завершённые reaction/view ключи сохраняют защиту от повторной реакции и доказательство просмотра;
- первая автоматическая очистка откладывается на один полный интервал и фиксирует grace-время в `app_settings`, чтобы успеть сделать backup PostgreSQL;
- очистка никогда не затрагивает `pending` и `running`.

Перед первым production-развёртыванием v1.0.23 сохраните backup PostgreSQL.

## Важное правило Railway

Запускайте **ровно одну реплику** LikeBot. Для PostgreSQL v1.0.24 удерживает advisory lock и завершит второй экземпляр с ошибкой до запуска worker. Это защищает очереди и аккаунты от двойного выполнения.

## Состояние системы и здоровье аккаунтов

Кнопка `📊 Статистика` теперь сначала открывает диагностический экран `🩺 Состояние LikeBot`. Он показывает:

- общий статус системы;
- активные, выключенные и проблемные аккаунты;
- состояние worker проверки сессий, мониторинга каналов, подписок, реакций и просмотров;
- число ожидающих и выполняющихся заданий;
- количество заданий, которые готовы к запуску более 5 минут;
- текущие FloodWait и сохранённые ошибки аккаунтов/целей.
- состояние критических уведомлений, интервал проверки и cooldown повторов.

Раздел `👥 Здоровье аккаунтов` сортирует аккаунты от наиболее проблемных к исправным. Оценка 0-100 является только внутренней оценкой операционной готовности LikeBot и не является рейтингом доверия Telegram.

Оценка использует только проверяемые признаки:

- недействительная сессия;
- ручное выключение аккаунта;
- активный FloodWait;
- сохранённая ошибка;
- нестандартный статус записи.

Исторические ошибки заданий отображаются для диагностики, но не уменьшают текущую оценку навсегда.

## Обновление данных аккаунтов

В разделе `👥 Мои аккаунты` доступна кнопка `🔄 Обновить`. Она последовательно проверяет сохранённые Telegram-сессии и заново получает профиль каждого аккаунта. Если владелец изменил имя или `@username`, карточка и кнопка аккаунта обновляются автоматически.

Проверка не меняет номер телефона и не создаёт новую сессию. Постоянно недействительная сессия переводит аккаунт в раздел `⚠️ Проблемные аккаунты`, не удаляя его телефон, имя, Telegram ID и завершённую историю. Временные сетевые ошибки только учитываются в итоговом отчёте. Клиенты, открытые только для обновления профиля, после проверки отключаются.

## Ручные просмотры последних публикаций

Начиная с v1.0.17 бот различает факт реакции и подтверждённый запрос просмотра. Завершённые реакции из старой базы, для которых невозможно доказать вызов просмотра, не блокируют ручную очередь просмотров. Новые реакции резервируют будущий просмотр, а после успешного `GetMessagesViewsRequest` сохраняют точную отметку подтверждения.

В карточке обычного канала доступна кнопка:

```text
👁 Добавить просмотры
```

Функция не требует выбора конкретного поста. Администратор выбирает один из фиксированных диапазонов:

```text
5 последних | 20 последних
50 последних | 100 последних
```

После этого задаётся количество аккаунтов на каждую публикацию:

```text
25% | 50% | 75% | 100%
или точное число, например 6
```

Бот получает последние канонические публикации канала, объединяет элементы одного альбома в один пост и адаптивно выбирает доступные подписанные аккаунты для каждой публикации с учётом их текущей нагрузки и уже запланированных действий текущего пакета. Текущая задержка реакций применяется между аккаунтами; выбранные публикации одного аккаунта выполняются подряд, начиная с самых новых. Это не умножает многоминутную задержку на каждую пару «аккаунт + пост».

Для пары `аккаунт + канал + публикация` не создаётся второе активное задание. Также учитываются ожидающие и выполненные реакции, потому что начиная с v1.0.14 реакция уже включает запрос просмотра. Ошибочные и отменённые задания можно безопасно запустить повторно.

Пока задача выполняется, кнопка в карточке канала показывает `⏳ Просмотры: N в очереди` и открывает её текущий статус. После завершения или остановки снова отображается `👁 Добавить просмотры`.

Карточка задачи показывает:

```text
📚 найдено публикаций
📦 создано заданий
⏳ ожидают / выполняются
✅ выполнено
⏭ уже учтено или запланировано
❌ ошибки
🛑 отменено
```

Кнопка `🛑 Остановить оставшиеся` отменяет только ещё не начавшиеся задания. Уже выполняющийся запрос завершается безопасно. После перезапуска контейнера задания `running` возвращаются в очередь, кроме остановленных пакетов.

Telegram самостоятельно решает, увеличивать ли публичный счётчик: повторный запрос от аккаунта, который уже видел публикацию вручную или через другую сессию, не гарантирует нового просмотра.

## Проблемные аккаунты

LikeBot проверяет активные сохранённые сессии сразу после запуска и затем каждые 15 минут.

При подтверждённой постоянной потере авторизации (`is_user_authorized() == False`, отозванная/дублированная auth key, удалённый или заблокированный Telegram-аккаунт) бот больше не удаляет запись. Он:

1. выключает аккаунт и ставит статус `unauthorized`;
2. сохраняет имя, телефон, Telegram ID, зашифрованную сессию и завершённую историю;
3. отменяет только его ожидающие/выполняющиеся задания подписок, реакций и просмотров;
4. переносит аккаунт в `👥 Мои аккаунты → ⚠️ Проблемные аккаунты`;
5. сохраняет время, причину и место обнаружения;
6. один раз уведомляет администратора.

В карточке доступны:

```text
🔄 Проверить повторно
🔐 Авторизовать заново
🗑 Удалить окончательно
```

Успешная повторная проверка или повторная авторизация возвращает аккаунт в активный пул и очищает отметку проблемы. Окончательное удаление выполняется только вручную после подтверждения.

Обычная ошибка сети, временная недоступность Telegram и FloodWait не считаются потерей авторизации. Ошибка расшифровки из-за неверного `SESSION_ENCRYPTION_KEY` также не должна автоматически удалять или карантинить аккаунт.

Проверка не держит все клиенты постоянно подключёнными: клиент, открытый только для проверки, после неё отключается.

> Аккаунт, который был физически удалён старой версией до установки v1.0.18, нельзя гарантированно восстановить из текущей базы. Для него потребуется резервная копия/старые логи либо повторное добавление.

## Добавление канала

1. Откройте `📢 Каналы`.
2. Нажмите `➕ Добавить канал`.
3. Отправьте `@username`, публичную ссылку или приватную invite-ссылку.

5. Создаст очередь подписки активных аккаунтов.

Бот повторно проверяет состояние перед запуском и создаёт задания только для активных аккаунтов, которые ещё не имеют завершённой или ожидающей подписки. Уже подписанные и находящиеся в очереди аккаунты не дублируются. Ошибочные и ранее завершённые выходом задания можно безопасно поставить на подписку повторно.

Если у канала уже есть ожидающая очередь, новые задания добавляются после её последнего задания. Если очереди нет, первый выбранный аккаунт запускается сразу, а следующие получают текущую задержку из `⏱ Задержка → 📢 Задержка подписки`.

Ручной выбор поддерживает до 100 управляемых аккаунтов, постраничную навигацию, выбор всех и сброс выбора.

## Добавление группы

1. Откройте `👥 Группы`.
2. Нажмите `➕ Добавить группу`.
3. Отправьте публичную или приватную ссылку.
4. Бот проверит, что ссылка ведёт именно на Telegram-супергруппу.
5. Группа появится отдельной кнопкой.

## Авто лайк

В разделе можно выбрать канал или группу и отдельно управлять:

```text
🆕 Новые посты: ВКЛ / ВЫКЛ
🕘 Старые посты: ВКЛ / ВЫКЛ
📚 Старых постов: 5 / 10 / 20 / 50
```

При включении новых публикаций бот запоминает текущий последний пост и обрабатывает только последующие сообщения.

В карточке также показываются число подписанных аккаунтов и состояние очереди реакций. Выключение новых постов отменяет только задания новых публикаций, а выключение старых - только задания старых публикаций.

### Лимит на пост

Кнопка `🎯 Лимит` задаёт максимальное количество **новых реакций от подключённых аккаунтов на одну публикацию**. Например, при 100 аккаунтах и лимите 25 бот выбирает до 25 наименее загруженных доступных аккаунтов для каждого поста, сохраняя случайный tie-break при одинаковых показателях. Реакции также выбираются случайно из набора канала или группы.

После подтверждения лимит применяется к будущим постам, включённым старым постам и уже ожидающим заданиям. Лишние ожидающие задания отменяются, недостающие создаются. Уже успешно поставленные реакции не удаляются, даже если их количество превышает новый лимит.

### ТФ и период раскрутки

Кнопка `📅 ТФ` открывает настройку `⏳ Период раскрутки`. Период относится ко всему выбранному каналу или группе, а не к одному посту:

```text
30
```

означает, что в течение 30 дней все включённые новые и старые посты получают реакции согласно лимиту, набору и задержке. После завершения срока новые задания больше не создаются, ожидающие задания отменяются, а режимы новых и старых постов автоматически выключаются.

Команда:

```text
постоянный
```

включает бессрочный режим. Реакции продолжают ставиться до тех пор, пока администратор сам не выключит новые или старые посты.

## Реакции

Главный раздел `😀 Реакции` управляет **реакциями по умолчанию**. Администратор может отправить эмодзи с любыми числовыми весами:

```text
👍60 ❤️20 🔥20
```

или эквивалентное соотношение:

```text
👍 6 ❤️ 2 🔥 2
```

В обоих случаях бот покажет и применит:

```text
👍 60% · ❤️ 20% · 🔥 20%
```

Сумма введённых чисел не обязана быть равна 100. Бот нормализует веса автоматически. Реакция с весом `0` отображается как `0%` и не выбирается. Если отправить только эмодзи без чисел, они получают равную вероятность. Отображаемые проценты округляются так, чтобы итог всегда составлял ровно `100%`.

Для каждого задания выбирается одна реакция с учётом настроенных весов. Настройка сразу применяется и к ожидающим заданиям, которые наследуют изменённый набор.

### Реакции конкретного канала

Откройте:

```text
📢 Каналы → нужный канал → 😀 Реакции канала
```

Сохранённые здесь реакции и вероятности действуют **только для выбранного канала**. Глобальный набор из главного меню не изменяется. Та же кнопка доступна внутри карточки `❤️ Авто лайк` этого канала. Кнопка `↩️ Использовать реакции по умолчанию` удаляет индивидуальную настройку и возвращает наследование глобального соотношения.

### Реакции конкретной группы

Откройте:

```text
👥 Группы → нужная группа → 😀 Реакции группы
```

Группа также может иметь собственные реакции и веса. Индивидуальные настройки каналов и групп независимы друг от друга и не перезаписываются при изменении глобальных реакций.

## Задержка

В главном разделе `⏱ Задержка` доступны два независимых диапазона:

```text
❤️ Задержка реакций
📢 Задержка подписки
```

- задержка реакций определяет, когда аккаунт поставит реакцию после создания задания;
- задержка подписки определяет интервал между аккаунтами при подписке и отписке;
- первый аккаунт в новой очереди подписки обрабатывается сразу, следующие получают накопительный интервал;
- значения сохраняются в PostgreSQL/SQLite и не требуют изменения Railway Variables.

Переменные `DEFAULT_REACTION_DELAY_*` и `JOIN_DELAY_*` используются только как стартовые значения, пока администратор не изменил диапазоны внутри бота. На экране каждого диапазона доступна кнопка `🔄 Пересчитать текущую очередь`, поэтому после обновления до v1.0.7 можно применить уже сохранённый диапазон без повторного ввода. После сохранения нового диапазона бот также предлагает два варианта:

```text
✅ Пересчитать текущую очередь
➡️ Только для новых задач
```

Для подписок и отписок при пересчёте первое ожидающее задание запускается сразу, а следующие получают накопительный случайный интервал. Для реакций каждое ожидающее задание получает новую независимую случайную задержку от текущего момента. Уже выполняющиеся задания не прерываются. Повторные попытки после `FloodWait` и временных ошибок не переносятся, чтобы не нарушить защитное время Telegram.

Задержки используются для управления очередью и соблюдения нагрузки. Они не отменяют и не обходят ограничения Telegram.

## Процент реакций по типу поста

В карточке обычного канала доступна кнопка `🖼 Типы постов`. Для выбранного канала отдельно задаются:

```text
🖼 С изображением: 100%
📝 Без изображения: 20%
```

Процент применяется после основного лимита `🎯 Лимит на пост`. Например, если подписаны 10 аккаунтов и лимит установлен на `Все`, то `20%` создаёт 2 задания реакции, а `100%` - 10. Если лимит равен 5, то `20%` создаёт 1 задание, а `100%` - 5.

Положительный дробный результат округляется вниз, но остаётся минимум одна реакция. Значение `0%` полностью отключает создание реакций для выбранного типа публикаций.

Изображением считается:

- обычное Telegram-фото;
- документ с MIME-типом `image/*`;
- альбом, в котором есть хотя бы одно изображение.

Текстовые посты, видео, аудио, опросы и другие публикации без изображения используют процент `Без изображения`. Настройка сохраняется отдельно для каждого канала и не влияет на глобальный набор реакций, другие каналы или группы.

## Обновление с v1.0.0-v1.0.13

Можно заменить файлы проекта новой версией, не удаляя PostgreSQL/SQLite базу. При старте бот автоматически:

- добавляет `channels.kind`, если колонки ещё нет;
- добавляет `join_jobs.action`, если колонки ещё нет;
- переводит `accounts.telegram_user_id` из PostgreSQL `INTEGER` в `BIGINT`;
- переводит `channels.telegram_channel_id` из PostgreSQL `INTEGER` в `BIGINT`;
- добавляет `reaction_jobs.source` для разделения заданий новых и старых постов;
- использует существующее `channels.reactions_json` для индивидуальных реакций каналов и групп; старые JSON-списки автоматически читаются как равные веса;
- добавляет `channels.max_reactions_per_post` для лимита новых реакций на одну публикацию;
- добавляет `channels.image_post_reaction_percent` и `channels.no_image_post_reaction_percent` с безопасным значением `100`;
- добавляет `reaction_jobs.post_has_image` для сохранения типа публикации и перерасчёта ожидающей очереди;
- добавляет `channels.promotion_mode`, `promotion_started_at` и `promotion_until` для таймфрейма раскрутки;
- добавляет nullable-поля `accounts.email_login`, `email_provider`, `email_note` и `email_updated_at` для учёта привязанной почты без паролей и кодов;
- возвращает прерванные при перезапуске задания из `running` в `pending`.

Существующие записи, очереди и настройки сохраняются. Для SQLite отдельное преобразование не требуется: SQLite хранит целые значения как 64-битные.

## Просмотр перед реакцией

Для обычных каналов каждая задача реакции теперь выполняется в строгом порядке:

```text
1. Аккаунт отмечает публикацию просмотренной.
2. Telegram принимает запрос просмотра или сообщает, что просмотр уже был учтён.
3. Только после этого аккаунт отправляет настроенную реакцию.
```

Запрос выполняется через пользовательскую Telegram-сессию с `increment=True`. Для супергрупп отдельный счётчик просмотров публикаций не используется, поэтому их реакции продолжают работать без такого запроса. Повтор одной и той же задачи не создаёт бесконечных просмотров: Telegram самостоятельно учитывает повторные запросы одного аккаунта.

Если запрос просмотра получил временную ошибку или `FloodWait`, реакция не отправляется раньше просмотра: существующий механизм повторов переносит всю задачу. Уже просмотренное сообщение не блокирует реакцию. Новые переменные Railway и миграции базы для этой функции не нужны.



## Расширенная аналитика v1.0.29

Кнопка `📊 Расширенная аналитика` на экране состояния открывает новый периодический отчёт. Доступны срезы `24 часа`, `7 дней`, `30 дней` и `Всё время`.

Отчёт показывает:

- успешные, ошибочные и отменённые подписки, реакции и просмотры;
- общий процент успеха без включения отменённых задач в знаменатель;
- текущие `pending/running` очереди;
- среднее опоздание запуска относительно `due_at` и среднюю длительность выполнения;
- рейтинг аккаунтов и каналов/групп по успешным действиям;
- отдельный список объектов с наибольшим числом ошибок;
- текущую нагрузку каждого объекта и динамику по дням;
- CSV в UTF-8 BOM с разделителем `;`, открывающийся в Excel.

Экран ограничивает рейтинг десятью строками, чтобы укладываться в лимит Telegram. CSV выгружает полный список известных аккаунтов и каналов/групп, включая объекты с нулевой активностью за выбранный период.

CSV не содержит телефонов, email, Telegram ID, ссылок, invite hash, `StringSession`, токенов или иных секретов. Текстовые ячейки защищены от формул Excel/LibreOffice. Все callback-периоды валидируются по строгому списку и неизвестные значения отклоняются.

Для периодов до 30 дней используются строки с точным `completed_at`. Архивные агрегаты без исходной даты включаются только в отчёт `Всё время`. Среднее время и дневная динамика во `Всё время` рассчитываются по подробным строкам, которые ещё не удалены retention-процессом. `join_jobs` хранит последнее состояние пары аккаунт/цель, поэтому подписки не являются полным append-only журналом переходов.

На существующих базах автоматически создаётся индекс `ix_join_jobs_status_completed_id`; новых таблиц, колонок и Railway Variables нет.


## Резервное копирование настроек v1.0.28

В `⚙️ Настройки -> 💾 Резервные копии` администратор может скачать подписанный JSON, проверить его перед восстановлением, применить только к уже существующим целям и открыть историю последних операций. Перед каждым восстановлением и откатом LikeBot сохраняет безопасный снимок состояния до изменения, поэтому действие можно отменить обратным откатом.

В переносимую копию входят:

- глобальные реакции и задержки;
- настройки существующих каналов и групп;
- профиль, лимит, индивидуальное окно, проценты типов постов и период раскрутки;
- только справочный маскированный список аккаунтов.

Не входят `StringSession`, Telegram-коды, пароль 2FA, токен бота, API-ключи, строка подключения к БД, email, сырые телефоны, приватные invite hash, очереди и содержимое сообщений. Список аккаунтов при восстановлении не меняет авторизацию и используется только для предварительного отчёта. Неизвестные цели пропускаются и не создаются автоматически.

Файл ограничен 2 МиБ и подписан `HMAC-SHA256` ключом, отдельно выведенным из `SESSION_ENCRYPTION_KEY`. Ручное редактирование файла или смена ключа приводит к безопасному отказу до транзакции. Полный физический backup PostgreSQL эта функция не заменяет: сырой дамп базы храните средствами Railway, потому что он содержит зашифрованные сессии и другие production-данные.

## Профили каналов v1.0.27

В карточке обычного канала и в его меню `❤️ Авто лайк` доступна кнопка `🎚 Профиль`. Профили не применяются к супергруппам.

- `🟢 Осторожный` — до 10 аккаунтов, распределение 30–60 минут, реакция/просмотр для 50% постов с изображением и 20% без изображения;
- `🔵 Обычный` — до 25 аккаунтов, распределение 15–30 минут, 80% и 50%;
- `🔥 Активный` — все доступные аккаунты, распределение 5–15 минут, 100% и 80%;
- `⚙️ Свой` — текущие параметры не совпадают полностью ни с одним готовым профилем.

Лимит готового профиля автоматически ограничивается `MAX_ACCOUNTS_PER_CHANNEL`. После подтверждения бот сохраняет все профильные поля одной транзакцией, затем согласует ожидающие реакции: задания без повторных попыток приводятся к новым процентам и лимиту и получают новый период. Задания с retry/FloodWait и уже выполненные действия не переписываются.

Профиль не меняет emoji и их веса, включение новых/старых публикаций, глубину старых постов, таймфрейм раскрутки и глобальную паузу конкретного аккаунта между действиями.

## Автоматическое восстановление v1.0.26

LikeBot может безопасно восстанавливать часть временных сбоев без ручного вмешательства:

- возвращать подтверждённо зависшие `running`-задания подписок, реакций и просмотров в очередь;
- завершать exhausted-задания как `failed`, не создавая бесконечных повторов;
- повторно проверять аккаунты после истёкшего FloodWait или временной ошибки;
- возвращать карантинный аккаунт только если сохранённая сессия снова авторизована и принадлежит тому же Telegram ID;
- пересоздавать недостающие задания подписки для восстановленного аккаунта;
- локально перезапускать stale/blocked worker с ограниченным числом попыток;
- передавать управление process supervisor/Railway, если локальное восстановление не помогло;
- сообщать администратору о неудачном восстановлении и о последующей нормализации.

Автовосстановление **не** запрашивает Telegram-коды, не вводит 2FA, не меняет Telegram-личность записи, не обходит FloodWait и не включает вручную выключенные аккаунты. Отменённые реакции и просмотры карантинного аккаунта не оживляются задним числом; после восстановления обычный планировщик создаёт новые задачи для новых публикаций.

Основные переменные:

```text
AUTO_RECOVERY_ENABLED=true
RECOVERY_CHECK_INTERVAL_SECONDS=60
RECOVERY_STUCK_AFTER_SECONDS=600
RECOVERY_MAX_JOBS_PER_CYCLE=100
RECOVERY_ACCOUNT_RECHECK_SECONDS=1800
RECOVERY_QUARANTINE_RECHECK_SECONDS=21600
RECOVERY_MAX_ACCOUNTS_PER_CYCLE=5
RECOVERY_ACCOUNT_CHECK_TIMEOUT_SECONDS=30
RECOVERY_WORKER_MAX_RESTARTS=3
RECOVERY_WORKER_RESTART_WINDOW_SECONDS=900
RECOVERY_WORKER_RESTART_BACKOFF_SECONDS=5
RECOVERY_WORKER_RESTART_COOLDOWN_SECONDS=300
MEMBERSHIP_ATTEMPT_TIMEOUT_SECONDS=180
VIEW_ATTEMPT_TIMEOUT_SECONDS=180
```

`RECOVERY_STUCK_AFTER_SECONDS` фактически не может быть меньше самого длинного attempt timeout плюс защитные 60 секунд. Это предотвращает возврат задания в очередь, пока Telegram-вызов ещё законно выполняется.

- смена `SESSION_ENCRYPTION_KEY` сделает старые сессии недоступными.

## Учёт привязанной почты

При добавлении нового Telegram-аккаунта порядок действий такой:

```text
➕ Добавить аккаунт
→ номер телефона
→ логин привязанной почты
→ подтверждение данных
→ код Telegram
→ пароль Telegram 2FA, если включён
```

Сохраняются только:

```text
📧 адрес почты
🏷 определённый почтовый сервис
📝 несекретное примечание администратора
```

Не сохраняются пароль почты, резервные коды, одноразовые коды и пароль Telegram 2FA. Для старых аккаунтов без адреса в `👥 Мои аккаунты` появляется раздел `📧 Без указанной почты`. Повторная авторизация не стирает уже сохранённую почту.
